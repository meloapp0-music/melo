# The room — who else was at this show

- Started: 2026-08-03
- Status: planned
- Last updated: 2026-08-03

## Context

The single biggest idea from the strategy pass, and the only one with neither
code nor design. Every comparable app has a version of it: Untappd shows who
else drank the same beer, Strava shows everyone who ran the same segment,
Letterboxd shows who else watched the film. Melo has nothing — a logged show
is a private row and the 90,000 other people who were in the building may as
well not exist.

It has stalled twice for the same reason: **there is no canonical event.**

`public.shows` (0001) is per-user and free-text:

```
id, user_id, artist text, date date, venue text, city text, ...
```

Two people at the same gig produce two unrelated rows. "The 1975" and
"the 1975", "Rose Bowl" and "Rose Bowl Stadium" never match. Without a way to
say *these are the same night*, there is nothing to count and nobody to show.

## Plan

### Event identity — derived now, canonical later

Do **not** wait for a canonical events table. Ship a derived key that works on
existing data today, and let precision accumulate.

**Phase 1 — `event_key`, a normalised derived string.**

Same shape as the existing entity keying in
[lib/ranking.js](../../src/web/lib/ranking.js) (`entityKeyOf`, `festivalKey`),
which already collapses a festival's many rows into one entity. Reuse that
normalisation rather than inventing a second one.

```
event_key = normalise(artist) || '|' || date || '|' || normalise(venue)
```

`normalise()`: lowercase, trim, collapse whitespace, strip punctuation, strip a
leading "the ", and strip trailing venue nouns (stadium, arena, theatre/theater,
hall, centre/center, club).

- **Date is exact.** A three-night run at the same venue is three rooms, and
  each night genuinely was a different show.
- **City is excluded.** The venue implies it, and city entry is the least
  consistent field in the table.
- Festivals keep using `festivalKey`; a festival *day* is its own room.

A generated column plus an index. No backfill, no external dependency, works
against every row already logged.

**Phase 2 — `event_id`, when it's free.**

`LogShow` already autofills from Ticketmaster and Setlist.fm, so a canonical id
is available at log time for a large share of new shows. Add a nullable
`shows.event_id` and an `events` table; populate it only when the show was
logged from an API result.

Room membership resolves on `event_id` when both rows have one, else
`event_key`. Precision improves over time without a migration cliff, and the
feature never depends on the resolver existing.

### Privacy — the part to get right

The room exposes where somebody was. The rule: **the room never reveals a row
the viewer could not already see.**

`shows.visibility` (`public` / `friends` / `private`, null = inherit from
`profiles`) and `public_profile` (0021) already govern this, and RLS already
enforces it. A plain select for room members is therefore correct by
construction — the security spine does the work, and no new policy is needed
for the named list.

The **aggregate count** is the exception and needs care. "12 people were here"
computed under RLS is not the interesting number; "1,247 were here" is. That
requires reading past RLS, so:

- a `security definer` function returning **only** `count(*)` for an
  `event_key` — never rows, never ids;
- suppressed below a floor (5) so a small room can't deanonymise anyone;
- never broken down by any dimension, since a count plus a filter is an
  identity leak.

### What it unlocks

- **Co-attendee linking** — "you and Sam have seen 6 shows together."
  `UserProfileView` already computes shows-in-common by fuzzy matching; the
  room makes it exact and turns it into a card.
- **The strangers line made real** — the pull quote in the mockups is
  "connected to 90,000 strangers". The room is the only feature that gives
  that a number.
- **Setlist confidence** — 40 rows on one `event_key` means a merged setlist
  beats any single person's memory.
- **Discovery** — people whose rooms overlap with yours are a far better
  friend suggestion than a contact-book match.

## Open questions / follow-ups

- Does the room belong on `ShowDetail`, or is it its own overlay? Leaning
  ShowDetail — it's an attribute of the night, not a destination.
- Opt-out: a per-user "don't count me in rooms" setting, separate from
  visibility. Probably needed before launch, cheap to add now.
- Multi-artist bills: an opener logged as its own show will not share an
  `event_key` with the headliner. Correct for ranking, wrong for the room.
  Possibly a second, looser `venue|date` key for "same building that night".
- The count floor of 5 is a guess. Worth checking against real data before
  launch.
